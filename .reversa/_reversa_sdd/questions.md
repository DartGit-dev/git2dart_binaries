## Question 5 — Android TLS consumer sequence

**Context:** the helper extracts a CA path but does not initialize libgit2 or apply `git_libgit2_opts_set_ssl_cert_locations`.
**Affected spec:** `_reversa_sdd/android-tls-bootstrap/requirements.md`

**Impact:** Defines the real HTTPS-readiness boundary and Android initialization policy.

**Status:** ✅ Answered in chat and by cross-repository evidence

**Answer:** Confirmed current Android owner: `git2dart/lib/src/platform_specific.dart:PlatformSpecific.androidInitialize()`. It executes `Libgit2.version` (managed libgit2 init) → `git2dart_binaries.AndroidSSLHelper.initialize()` (CA extraction) → `Libgit2.setSSLCertLocations(file: certPath)` (native configuration). The API is publicly exported but no production caller was found; application startup must invoke it. Concurrent first `PlatformSpecific.initialize()` calls must be serialized for both Android and iOS: one shared in-flight operation runs and all other callers await it. The current iOS path is `PlatformSpecific.iosInitialize()` → `Libgit2.version`; no existing shared in-flight implementation was found.

## Question 7 — Windows OpenSSL provenance

**Context:** Android/iOS/macOS consume OpenSSL 3.0.15, while Windows discovers and fingerprints the runner-installed version.
**Affected spec:** `_reversa_sdd/native-build-bindings-generation/requirements.md`
**Question:** Should Windows continue using the runner OpenSSL version, or must it build/use the same explicit 3.0.15 pin?
**Impact:** Defines cross-platform native-version reproducibility and cache identity.

**Status:** ✅ Answered in chat and by workflow evidence

**Answer:** The target policy is to build the explicitly pinned required OpenSSL version from source for every platform, including Windows. Current Windows CI does not do that: it discovers and fingerprints a runner-installed OpenSSL version, then copies its DLLs. If a source build is infeasible on a path, release validation must require that path to use the exact same OpenSSL version as every other platform. An arbitrary runner-installed Windows version is never acceptable.

**Status:** ✅ Answered in chat

**Answer:** `git2dart_binaries` owns and pins the underlying libgit2 version. `git2dart` declares/selects the compatible major-version line of `git2dart_binaries`. Compatibility is governed by major versions; minor releases are fixes within the already selected libgit2 version line and do not redefine the cross-package compatibility boundary. `git2dart` owns the single GitHub Actions release/build coordination point. Its integration tests must fully validate the exact selected `git2dart` + `git2dart_binaries` pair as resolved and used by the client; feature CI gates merge, and a separate green `main` CI/CD run gates publication. This is a user-confirmed policy, not current workflow/run proof.
